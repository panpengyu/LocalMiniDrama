# 并发竞态风险预防审计报告

> 背景：H1–H7 的资金/配额竞态修复完成、通用原子占位（`utils/atomicQuota.js` + `middleware/atomicQuotaGuard.js`）已通过 4/8 实例压测验证后，对 `backend-node/src/services/` 全量服务做的一次「同类竞态」体检，目标是在多实例部署前把剩余 TOCTOU 隐患提前暴露并给出与既有修复一致的整改方向。
>
> 审计范围：`backend-node/src/services/` 全部服务文件。
> 已排除（本轮已修复，不再重复）：quotaService（H1/H7）、paymentService（H2）、marketplaceService（H3）、creatorService（H4/H5）、collaborationService（H6）。

---

## 0. 总体结论

- **资金/账本类写入全部安全**：积分 `point_logs`、创作者账本、提现 `withdrawals`、订单 `orders` 均已采用「原子自增 `SET x = x + ?`」「锚点行 `FOR UPDATE`」「条件 UPDATE（WHERE 带状态/余额）」等正确模式，**未发现资金丢失更新**。
- 剩余风险集中在两类**非资金**场景：**① 工作流审批状态机重复执行**、**② AI 生成任务 `processing` 抢占仅靠内存去重**。二者在当前「单进程 + sync-mysql 单连接」下被串行掩盖，**一旦切多实例/连接池就会暴露**（与连接池配置建议文档 §3 同源）。
- 另有一处 **check-then-insert 完全无数据库唯一约束兜底**（frame_prompts），多实例下会产生重复行。

风险分级速览：

| 级别 | 模块 | 问题 | 多实例下后果 |
|------|------|------|--------------|
| 🔴 高 | `workflowService.reviewStep` | 状态机 guard→UPDATE 无条件、无事务 | 重复审批、reviewer 覆盖、实例进度错乱 |
| 🟠 中 | `imageService`/`videoService`/`bgmService`/`videoMergeService` 的 `processing` 抢占 | guard 读 pending 后无条件 UPDATE | 重复调用外部 AI，**重复计费/耗额度** |
| 🟠 中 | `storyboardService.saveFramePrompt` | check-then-insert 且表无 UNIQUE | 同一 (storyboard, frame_type) 产生重复行 |
| 🟡 低 | `authService.register` 等 | 有 DB 唯一约束兜底，仅错误处理不友好 | 不脏数据，撞约束抛原始异常 |

## 1. 🔴 高危：workflowService.reviewStep —— 审批状态机重复执行

**位置**：`src/services/workflowService.js:266-314`，函数 `reviewStep()`

**问题**：guard 与写入之间存在 TOCTOU 窗口，且写入无条件、无事务。

```js
if (stepLog.status !== STEP_STATUS.REVIEWING) {      // ← 274 读判定
  throw new Error('[WF-REV-002] 该步骤不在审核状态');
}
...
db.prepare('UPDATE workflow_step_logs SET status = ?, reviewer_id = ?, ... WHERE id = ?')
  .run(STEP_STATUS.COMPLETED, ..., stepLog.id);        // ← 284 WHERE 只有 id，无 status 条件
db.prepare('UPDATE workflow_instances SET status = ?, current_step_index = ?, ... WHERE id = ?')...
```

**后果**：两个并发审批（含一个 approve + 一个 reject）都能读到 `REVIEWING` 通过 guard，随后都执行流转 → 重复推进实例、覆盖 `reviewer_id`/`review_note`、甚至产生「既 completed 又 failed」的错乱状态。

**整改方向**（对齐本库已验证范式 `templateReviewService.manualReview`）：把状态前置条件下沉进 UPDATE 的 WHERE，用 `changes===1` 判定并发唯一赢家，并用事务包裹两条 UPDATE：

```js
const runTx = () => {
  const nextStepStatus = approved ? STEP_STATUS.COMPLETED : STEP_STATUS.FAILED;
  // 条件 UPDATE：仅当仍为 reviewing 才流转；changes===0 说明已被其它并发审批处理
  const changed = db.prepare(
    'UPDATE workflow_step_logs SET status = ?, reviewer_id = ?, reviewed_at = ?, review_note = ? WHERE id = ? AND status = ?'
  ).run(nextStepStatus, reviewerId || null, nowStr(), note || null, stepLog.id, STEP_STATUS.REVIEWING).changes;
  if (!changed) throw new Error('[WF-REV-002] 该步骤已被处理');
  // ...随后再更新 workflow_instances 进度
};
db.transaction ? db.transaction(runTx)() : runTx();
```

## 2. 🟠 中危：AI 生成任务 `processing` 抢占仅靠内存/无条件 UPDATE

**同一模式，多处命中**——先 `SELECT status` 判 pending，随后**无条件** `UPDATE SET status='processing' WHERE id=?`：

| 文件 | 位置 | 说明 |
|------|------|------|
| `imageService.js` | `595`(guard)→`611`(抢占) | `processImageGeneration` |
| `videoService.js` | `372-387` | 靠内存 `activeVideoPolls` Set 去重，非 DB 层；另见 `295-301` resume |
| `bgmService.js` | `387`(guard)→`397`(抢占) | BGM 生成 |
| `videoMergeService.js` | `166-178` | 无 guard，直接置 processing |

**后果**：单进程串行下安全；**多实例/连接池下**两个 worker 会同时读到 `pending` 并都发起外部 AI 调用 → **重复计费、重复耗用额度**、产物覆盖。

**整改方向**：把抢占改成**条件 UPDATE + changes 判定**，谁 `changes===1` 谁才是本进程的执行者：

```js
const claimed = db.prepare(
  "UPDATE image_generations SET status='processing', updated_at=? WHERE id=? AND status='pending'"
).run(now, imageGenId).changes;
if (!claimed) { log.info('[图生] 已被其它实例抢占，跳过', { id: imageGenId }); return; }
// claimed===1 才继续调用外部 AI
```

内存去重（`activeVideoPolls`）可保留作为**同进程内**的快速短路，但**不能作为跨实例的唯一防线**，必须叠加上面的 DB 条件抢占。

## 3. 🟠 中危：storyboardService.saveFramePrompt —— 无约束的 check-then-insert

**位置**：`src/services/storyboardService.js:227-246`

```js
const existing = db.prepare('SELECT id FROM frame_prompts WHERE storyboard_id = ? AND frame_type = ?').get(...);
if (existing) { /* UPDATE */ } else { /* INSERT */ }
```

`frame_prompts` 表**无 `UNIQUE(storyboard_id, frame_type)` 约束**（`migrations/01_init.sql`），无事务兜底。多实例并发保存同一 (storyboard, frame_type) 会产生**重复行**，`getFramePrompts` 可能读到脏数据。

**整改方向**（二选一，推荐同时做）：
1. **加数据库唯一约束** `UNIQUE(storyboard_id, frame_type)`（需 SQLite/MySQL 双库迁移），再把写入改为「INSERT ... 捕获 duplicate → 转 UPDATE」的幂等模式；
2. 或用本库既有的 upsert 兼容写法（参考 `commentService` 的 `INSERT + catch unique`）。

## 4. 🟡 低危：有唯一约束兜底、仅错误处理可优化

以下都有 DB 唯一约束/主键**保证不产生脏数据**，仅并发撞约束时抛的是原始异常而非友好业务提示，属可选优化：

| 文件 | 位置 | 约束 | 建议 |
|------|------|------|------|
| `authService.register` | `65-94` | `users.phone UNIQUE` | try/catch 捕获 duplicate → "该手机号已注册" |
| `ttsService.bindVoice` | `301-334` | `UNIQUE(drama_id, character_id)` | 同上，catch unique 转 UPDATE |
| `userLifecycleService.computeAndSave` | `148-173` | `user_id` PK | 调用为管理端/定时，风险极低 |
| `characterGenerationService` | `126-189` | 无（按名字查重） | 边缘场景，可加 task 内串行保证 |

已正确实现幂等（**无需改动**）：`materialTagService.ensureTag/relateTag`（catch unique 回查）、`commentService`（@提及/已读 INSERT+catch）、`financeService.notifyArrears`（dedup_key + catch）。

---

## 5. 建议的整改优先级

1. **P0 — `workflowService.reviewStep`**：影响审批正确性，改造成本低（照抄 `templateReviewService` 范式），建议立即修。
2. **P1 — AI 生成 `processing` 抢占**（image/video/bgm/merge）：多实例上线**前必须**改条件抢占，否则直接对应「重复计费」资损。
3. **P2 — `frame_prompts` 唯一约束**：加约束 + 幂等写入，随下一次迁移一起做。
4. **P3 — 低危错误处理优化**：择机顺手改善用户提示。

> 三类高/中风险的共性根因与 H6/H7 完全一致——**「读判定」与「写入」不在同一原子操作内**。整改范式也一致：要么条件 UPDATE 用 `changes` 判赢家（状态机/抢占），要么唯一约束 + INSERT 幂等（check-then-insert），要么走 `atomicQuota.tryConsumeBounded`（累计型配额）。多实例部署前建议至少完成 P0 + P1。
