# 多实例部署 · 数据库连接池配置建议

> 目标：为未来将 LocalMiniDrama 后端从「单进程单连接」升级为「多实例横向扩展」提供数据库连接与锁的配置基线，从根上防止类似 H6/H7 的**锁失效 / 配额超发**问题重现。
>
> 关联修复：`backend-node/src/utils/atomicQuota.js`（通用原子占位）、`backend-node/src/middleware/atomicQuotaGuard.js`（通用中间件）。

---

## 1. 现状诊断（为什么会有隐患）

| 项 | 现状 | 风险 |
|----|------|------|
| MySQL 驱动 | `sync-mysql`（`backend-node/src/db/index.js`），**单个同步连接**，非连接池 | 单实例并发吞吐受限；多实例下每实例仍只有 1 条连接，事务排队成瓶颈 |
| 连接池参数 | `config.yaml` 已声明 `database.max_idle: 10` / `max_open: 100`，但 **驱动未消费这两个值** | 配置形同虚设，扩容后无法调优 |
| 事务隔离 | 事务内显式 `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` + 写前 `FOR UPDATE` 行锁 | 机制正确，但依赖「同一连接串行执行 BEGIN/COMMIT」；换池后必须保证**一次事务内所有语句走同一条物理连接** |
| 原子占位锁 | 锁定恒存在的父级锚点行（`users` / `dramas`）的 `FOR UPDATE` 行锁 | 行锁由 **MySQL 服务端**持有，天然跨实例生效——只要多实例连的是**同一个 MySQL 实例**，锁不会失效 |

**结论**：锁语义本身跨实例安全（服务端行锁）。真正的多实例风险有三：
1. 连接池未启用 → 无法承载多实例并发；
2. 若引入池，事务语句可能被分散到不同物理连接 → `BEGIN`/`FOR UPDATE`/`COMMIT` 错位 → **锁失效**；
3. 若未来分库 / 多写库（多个 MySQL 主库），服务端行锁不再是同一把 → 需改用分布式锁。

---

## 2. 连接池配置基线（推荐值）

以「N 个后端实例，单个 MySQL 主库」为前提。

### 2.1 config.yaml 建议

```yaml
database:
  type: mysql
  host: localhost
  port: 3306
  user: root
  password: root
  database: localminidrama
  # —— 连接池（每个实例） ——
  max_open: 20          # 每实例最大连接数：建议 = (核心数 * 2) ~ 25，不宜过大
  max_idle: 5           # 每实例空闲保活连接数：max_open 的 1/4 ~ 1/2
  conn_max_lifetime: 1800   # 连接最大存活秒数（30min），规避 MySQL wait_timeout 断连
  conn_max_idle_time: 600   # 空闲连接回收秒数（10min）
  queue_limit: 0            # 取连接排队上限，0 = 不限（由上游超时兜底）
  acquire_timeout: 10       # 获取连接超时秒数，超时快速失败而非无限阻塞
  # —— 事务与锁 ——
  isolation_level: READ-COMMITTED   # 与现有原子占位事务口径一致
```

### 2.2 容量测算公式

```
MySQL 服务端 max_connections  ≥  实例数 N × 单实例 max_open  +  预留(运维/备份/监控 ≈ 20)
```

示例：4 个实例 × `max_open=20` = 80，`max_connections` 建议设 `≥ 120`（默认 151 够用）。

> ⚠️ 反模式：把 `max_open` 设成 100（当前 config.yaml 的遗留值）。4 实例即 400 连接，极易打爆 MySQL 默认 `max_connections=151`，触发 `Too many connections`，反而制造雪崩。

### 2.3 MySQL 服务端配合参数

```ini
[mysqld]
max_connections        = 200        # 覆盖 N × max_open + 预留
wait_timeout           = 28800      # 需 > conn_max_lifetime，避免服务端先断
interactive_timeout    = 28800
innodb_lock_wait_timeout = 10       # 行锁等待超时，防止原子占位事务相互长时间死等
transaction_isolation  = READ-COMMITTED
innodb_deadlock_detect = ON         # 保留死锁检测，配合应用层重试
```

## 3. 迁移到连接池时的**强制约束**（防止锁失效）

现有原子占位（`atomicQuota.runWriteSerialized` → `BEGIN` + `FOR UPDATE` + `COMMIT`）在**单连接**下天然安全。换成连接池后，必须满足以下不变式，否则锁会失效：

1. **事务连接绑定（最关键）**：一次事务内的 `BEGIN → SELECT ... FOR UPDATE → INSERT → COMMIT` 必须在**同一条物理连接**上执行。
   - 推荐迁移到 `mysql2` 连接池，用 `pool.getConnection()` 取出连接，全事务复用该 `connection`，`finally` 里 `release()`。
   - `db.transaction(fn)` 的包装需改为：取连接 → 绑定给 `fn` 内所有 `prepare` → 释放。**禁止**事务内不同语句各自从池里随机取连接。

2. **锚点行锁不可省**：`SELECT <pk> FROM <anchor> WHERE <pk>=? FOR UPDATE` 必须保留。这是「从空计数（used=0）起始」并发安全的唯一保证——无既有子行可锁时，靠锁父级锚点行串行化。（见 `atomicQuota.js` 顶部「关键陷阱」注释。）

3. **单一写库前提**：上述行锁跨实例生效的前提是**所有实例连同一个 MySQL 主库**。一旦出现多写库 / 分库分表，行锁不再互斥，必须升级为分布式锁（见 §5）。

4. **短事务**：原子占位事务内**只做** count + 写入，严禁夹入 AI 调用、HTTP、文件 IO 等慢操作（现有实现已将 `afterDramaCreated` 等副作用放在事务外，须延续此约定）。否则行锁持有时间拉长 → `innodb_lock_wait_timeout` 频发。

5. **应用层重试**：为死锁 / 锁等待超时（`ER_LOCK_DEADLOCK` / `ER_LOCK_WAIT_TIMEOUT`）加**幂等重试**（指数退避 2~3 次）。原子占位是幂等的（超限返回 false，不产生副作用），可安全重试。

## 4. 分环境推荐配置

| 环境 | 驱动 | 实例数 | max_open | max_idle | max_connections |
|------|------|--------|----------|----------|-----------------|
| 本地开发 | SQLite / sync-mysql | 1 | —（单连接） | — | — |
| 测试 / 预发 | mysql2 pool | 2 | 15 | 4 | 100 |
| 生产（横向扩展） | mysql2 pool | 4 | 20 | 5 | 200 |
| 生产（大并发） | mysql2 pool | 8 | 15 | 4 | 200~300 |

> SQLite（`better-sqlite3`）为嵌入式**单文件单进程**，**不支持多实例共享写**。多实例部署必须切换到 MySQL；SQLite 仅保留给本地开发 / 单机部署。

## 5. 演进路线（何时该上分布式锁）

```
阶段一：单实例 + sync-mysql 单连接              ← 当前
        原子占位（BEGIN IMMEDIATE / FOR UPDATE 锚点锁）已足够

阶段二：多实例 + mysql2 连接池 + 单一 MySQL 主库   ← 本文档目标
        服务端行锁跨实例互斥；须满足 §3 全部约束

阶段三：多写库 / 分库分表 / 跨地域              ← 未来
        行锁不再同库互斥，改用：
          - Redis 分布式锁（Redlock，本项目已依赖 Redis，见 config.yaml redis 段）
          - 或数据库唯一约束 + 幂等键（配额场景可用「配额账本表 + 唯一键」硬约束兜底）
```

**建议**：阶段三优先考虑「唯一约束 / 条件更新硬兜底」而非纯分布式锁——参考 `quotaService.tryConsumeGenerationBounded`（`UPDATE ... WHERE used < limit` 条件自增 + 唯一键 INSERT）的做法，它不依赖任何锁即可跨实例防超发，是分库场景下最稳的模式。

## 6. 落地检查清单

- [ ] 将 MySQL 驱动从 `sync-mysql` 评估迁移到 `mysql2`（连接池 + Promise/回调）
- [ ] `config.yaml` 的 `max_open` 从 100 下调到 20；新增 `max_idle` / `conn_max_lifetime` / `acquire_timeout`
- [ ] 事务包装保证「同一事务同一连接」（`getConnection` → 复用 → `release`）
- [ ] 保留 `atomicQuota` 锚点行锁 `FOR UPDATE`，不得删减
- [ ] MySQL 服务端 `max_connections ≥ N × max_open + 预留`
- [ ] 为死锁 / 锁超时加幂等重试（利用原子占位的幂等性）
- [ ] 原子占位事务内禁止慢操作（AI / HTTP / IO 放事务外）
- [ ] 多实例回归：并发创建项目（H7）/ 并发邀请协作者（H6）压测，验证 `used ≤ limit` 恒成立

## 7. 配套压测脚本（多实例锁竞争实证）

已提供可执行脚本 `backend-node/scripts/stress_pool_lock_contention.js`，用**多进程 fork 模拟 N 个部署实例**（每进程独立 `getDb()` 连接，全部连同一 MySQL 主库），在起跑栅栏对齐后并发争抢同一配额边界，直接验证 §3 结论：

```bash
cd backend-node
node scripts/stress_pool_lock_contention.js                     # 4 实例 × 3 轮，项目数(H7)+协作(H6)
node scripts/stress_pool_lock_contention.js --instances 8 --rounds 5
node scripts/stress_pool_lock_contention.js --only collaborator # 仅测「从空(used=0)并发」最易超发场景
node scripts/stress_pool_lock_contention.js --clean             # 清理压测残留
```

断言：`A 放行数 == 起始剩余名额`（零超发）、`B 终态行数 == limit`（精确封顶）、`C 无 DB 异常`（失败均为满额拒绝，非锁失效）。退出码 0 全通过 / 1 存在超发。

**实测结论（4 与 8 实例）**：H7 剩余 3 名额并发 → 恰好放行 3 封顶 15；H6 从空 8 实例并发抢 1 名额 → 恰好放行 1 拒绝 7，全程零 DB 异常。**印证多实例连同一主库时父级锚点行 `FOR UPDATE` 行锁跨实例互斥、锁未失效。**
